# UI (macOS)

> All the screens in Rem for Mac. Includes the small popover you see when clicking the menu bar icon, the main window with Agenda/Inbox/Sessions/Settings sidebar rows plus a distinct "Chat" primary action, shared skills settings, paired devices, permissions, and sign-in. Most task views (Agenda, Inbox), skills settings, and the chat surface itself are shared with iOS and only lightly wrapped here.

SwiftUI views for Rem for Mac — main window, menu bar extra, chat, settings wrappers, task management, shared skills surfaces, device pairing, and permissions.

| `MainWindow.swift` | Primary window with NavigationSplitView sidebar (Agenda, Inbox, Sessions, Settings) + a distinct **"Chat" primary action** at the sidebar footer. Chat is intentionally NOT a sidebar row — reached via "Chat" button or by selecting a past conversation in the Sessions tab. The shell owns explicit sidebar visibility and relies on standard macOS sidebar commands instead of adding a duplicate toolbar toggle. Authentication gate shows `MacSignInView` if not signed in. Agenda, Inbox, Sessions, and Chat all enter through native `NavigationStack` detail hosts so route titles and toolbar items resolve through the same macOS navigation chrome. | `MacChatWindow.swift` | Chat interface using the shared `SharedRemChatView` (same custom UI as iOS: speech bubbles, thinking blocks, inline tool result cards, Grok-style composer). Every explicit Chat/New Chat doorway mints a fresh `chat-*`; a Sessions row opens exactly its selected existing key. Only the Agenda Summary/brief product surface may enter the backend-advertised durable conversation, and only that durable orchestrator session can render current-day atomic brief-bound suggestions. Suggestion scope includes account, backend, and the effective active local/cloud gateway identity, so a retained cloud URL cannot authorize state while the local override owns the connection; the window consumes the single suggestion and task stores injected by `MainWindow`. Three-tier gating is authentication → connection → operator ready. The brief post-operator view-model initialization gap uses shared `ChatConnectionLoadingView`, never a separate spinner. Session navigation passes the requested route key and freshness separately from the asynchronously switching view model so the shared transcript gate cannot flash the previous chat. Cloud, manual, and local chats require the active runtime's structured usable-auth response. Raw local auth-profile inventory, catalog membership, and Keychain mirrors never authorize a provider; an older local runtime without the availability method fails closed for explicit selections while Automatic remains compatible. Loading/failure is distinct from verified empty: a refresh retains only same-session/candidate verified evidence, while an unknown new session blocks explicit provider Send. A monotonic operator-session generation invalidates evidence before credential/socket replacement, including same-URL token/account swaps; foregrounding, gateway-event/local-auth revisions, and a bounded 60-second refresh re-probe without destructively clearing a valid snapshot. Manage Models receives the same tri-state evidence and active gateway session, so unknown evidence shows recovery rather than false-empty provider copy and Automatic/MiniMax writes remain authoritative across devices. The window owns one `MacQuotaService` for text and Talk Mode: shared pre-dispatch hooks enforce both daily and monthly exhaustion before composer/audio mutation, authoritative denials publish an observable unlock at their UTC reset boundary, and expired scoped evidence never falls back to the retained summary zero. Missing/stale billing truth reaches the backend gate without Free-plan inference. Each chat transport owns an exact quota dispatch context and retires its token only after the gateway acknowledges the accepted `chat.send` run. Ambiguity uses explicit do-not-retry banner copy instead of the shared daily-limit upgrade claim. The window also lazy-owns `RemMacTalkModeManager` and wires its state into the shared view. ## Patterns & Conventions

- **Environment injection**: All views access `MacGatewaySessionManager` via `@Environment`. No prop drilling.
- **Sessions IA decision (#709)**: Keep **Sessions** as a top-level sidebar row. It is the durable conversation-history and rename/delete surface, and selecting a row opens Chat with that session active. Keep **Chat** out of the sidebar list as the primary footer action for starting a new conversation; menu-bar and app-command routes may still open Chat directly. Do not move conversation history into a secondary Chat sublist unless the whole main-window IA is reconsidered.
- **Task refresh pattern**: `.task { await refreshTasks() }` + `.onChange(of: session.operatorReady)` for reactive refresh when operator readiness changes. Top-level Mac surfaces should not expose manual refresh as primary chrome unless a view has a clear recovery-only reason.
- **Navigation titles**: Main detail surfaces should use native navigation titles rather than drawing duplicate in-content page headers. Chat is also hosted in a `NavigationStack`: unavailable/loading states use the fallback `Chat` title, while the loaded shared chat surface supplies the current conversation title.
- **Settings child titles**: Settings child routes own their native navigation title. Root Settings stays titled `Settings`; detail routes such as Permissions, Billing & Usage, Connectors, Gateways, Backup, and Capabilities set their own titles instead of inheriting parent chrome or drawing page headers inside the form.
- **Task editor chrome**: Task creation sheets use native navigation chrome: `NavigationStack`, grouped `Form`, navigation titles, and cancellation/confirmation toolbar items. Detail-route edits should stay inline when the edit is scoped to one section, such as task scheduling. Avoid custom in-form header bars that duplicate macOS sheet/title affordances.
- **Task detail chrome**: Agenda and Inbox task rows should open inline detail routes, not modal detail sheets. Detail routes use title-case native navigation titles (`Task Details`, `Event Details`) and keep primary completion in the toolbar instead of duplicating it as an in-form action row. Keep narrow toolbar actions icon-sized with `.help` and accessibility labels so title and action chrome do not crowd each other. Schedule and reschedule controls expand inline in the `When` section so task editing stays inside the detail route; successful schedule changes return to the list so rows refresh from `MacTaskStore`.
- **Task detail editing scope (#710)**: Keep single-section edits, such as schedule/reschedule, inline inside the owning section. For deeper task edits beyond scheduling, use a detail-column edit state in `MacTaskDetailView` instead of a generic modal sheet or a separate editor route; the first editable task fields should be title, notes, priority, category, due date, and start date. Calendar-event field editing stays unavailable on Mac, apart from the existing remove action, until there is an explicit writable calendar-provider contract for event title/time/location/calendar updates, because `MacTaskStore` only owns Rem task REST mutations today.
- **Conditional rendering**: Loading, error, empty, and content states are used consistently across agenda, inbox, shared skills, and devices views.
- **Adapter pattern**: `MainWindow` wraps `MacTaskStore` in `MacTaskStoreAdapter` to conform to shared `TaskStoreProviding` protocol.
- **Context menus**: Task rows support right-click actions (complete, snooze, delete) via `.contextMenu`.
- **Static formatters**: `DateFormatter` instances stored as `static let` properties to avoid recreation.
- **RPC communication**: Gateway-backed settings surfaces use `chatSession.request(method:paramsJSON:)` for gateway RPC calls.
- **Modal sheets**: Actions like task creation and skill detail use `.sheet(isPresented:)` / `.sheet(item:)`.
- **Settings vs gateway detail**: Root Settings is for account/app-level preferences and cross-gateway overview. Gateway Detail owns gateway-scoped lifecycle, pairing, backup/restore, capabilities, updates, logs, and risk-bearing actions. Platform-specific rows such as Mac Backup should live in Gateway Detail unless the same global account concept exists on iOS too.
- **Permissions vs Connectors**: Permissions is for local macOS device access: Accessibility, Screen Recording, Microphone, Speech Recognition, and Notifications. Calendar readiness is managed in Connectors, including local Apple Calendar and provider-backed calendars such as Google Calendar, so users do not confuse account/capability readiness with this Mac's TCC grants. When account context is available, the Permissions Calendar guidance should navigate to Connectors instead of remaining a static explanation. Voice readiness owns microphone and speech grants; push-to-talk and global hotkey support remain Accessibility-scoped.

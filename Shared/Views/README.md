# Shared/Views

Cross-platform SwiftUI views used by both iOS and macOS targets. Gateway
surfaces are generic over `GatewaySessionProviding`; task surfaces are generic
over `TaskStoreProviding`.

## Files

`Chat/ChatConnectionLoadingView.swift` owns the canonical `ChatConnectionRecoveryCard` used by
Chat Sessions, the pre-view-model chat bridge, and initialized chat. It is the only chat connection
error presenter and preserves `Retry` plus `Review Connection`; platform shells must yield their
global recovery banner while one of those chat surfaces owns presentation.

| `Settings/SharedComposioConnectionsView.swift` | Shared Connectors surface for Composio-backed apps. Productivity and messaging integrations share one real toolkit catalog and one connect/pause/revoke lifecycle; do not add a separate hard-coded Channels section. Provider grant state remains separate from gateway readiness: a committed ACTIVE grant reads `Connected • Activating…` while bounded backend reconciliation continues, `Connected • Runtime unavailable` after a known failure, and only `Connected • Active` after the gateway acknowledges the hosted-MCP scope. The status poll runs to a terminal state on BOTH axes (`ComposioConnectPollDriver`), the grant phase and the gateway-runtime phase holding separate attempt budgets so a slow OAuth cannot consume the runtime's. A committed grant nearly always arrives with `runtimeSyncing: true`, because the route bounds its runtime observation to ~2s while the first wire after a new grant has to mint a Composio session and patch the gateway config — work `composio.service.ts` measures at 15-67s on this fleet. Treating the committed grant as terminal therefore stranded a freshly connected row on `Connected • Activating…` with nothing to promote it, since the foreground re-check skipped anything already reading as connected; that re-check now treats connected-but-syncing as unfinished, and retiring a poll also retires its connect attempt's admission gate and spinner. Slow provider lifecycle work returns explicit `mutationStatus: unknown` before the HTTP client deadline without claiming acceptance or process-local durability, so the requested state is not falsely rolled back; catalog refresh cannot replace an in-flight mutation with pre-mutation truth, and an incomplete pause reads `Connected • Updating…` until a later authoritative catalog read confirms completion. A synchronous per-toolkit attempt-generation gate prevents rapid pre-redraw taps from creating multiple hosted OAuth sessions; teardown invalidates that ownership plus poll generations, so cancellation-ignoring connect/status work cannot later open a browser, install a poll, publish state, or block a fresh re-entry. Connect admission and the connected-status transition advance the catalog generation fence before publishing OAuth/runtime truth, so a delayed pre-connect GET cannot erase the new connection; the fence advances once at that transition rather than on every subsequent runtime publication, which would keep retiring catalog loads the user had legitimately triggered. Poll responses and exhausted/error cleanup are additionally fenced by both connection ID and per-poll generation after every await, preventing cancellation-ignoring replaced polls from publishing or clearing a newer task's spinner; pause and disconnect advance that generation at admission before publishing mutation state. Composio's `discord` user grant is labeled Discord and remains distinct from the bot-oriented `discordbot` grant labeled Discord Bot. WhatsApp is labeled Business because Composio does not support personal accounts, and Telegram uses a custom `API_KEY` auth-config schema whose bot token is collected only by Composio's hosted Connect Link. There is no second Channels product and no legacy-channel doorway: the native Discord/WhatsApp connector stack was deleted once this catalog covered the same providers, and `backend/src/scripts/revoke-native-channels.ts` is the one-shot that turns off any connector an older build had enabled. `MainWindowScreenRouteTests` pins the absence so a parallel Channels surface cannot be reintroduced beside this one. `ConnectorAppsPresentationState` keeps loading/error/empty/content states truthful on iOS and macOS. |

| `Settings/SharedAutomationsSettingsView.swift` | Shared Automations overview and built-in Daily Brief detail. The three backend check-in slots are the authoritative triggers of one Daily Brief automation; its parent status is derived and read-only so pausing cannot destroy trigger selection. Parent and detail share one generation-aware store: a trigger mutation invalidates older GETs, refresh during a PUT retains optimistic controls while incorporating newer run evidence, mutation completion invalidates every pre-completion refresh before releasing its fence, and a failed write rolls back only the mutation it still owns. Settings exposes those triggers, read-only built-in instructions, and the server-derived Inputs and Outputs sections. **Inputs are not authored in the app.** They come from `GET /api/v1/automations/:kind/inputs` through `AutomationInputsService`/`AutomationInputsStore`: the server derives `included` / `not_connected` / `unavailable` / `coming_soon` from its own connector descriptors, the user's ACTIVE Composio accounts, and the last collect recorded in `daily_brief_artifacts.input_manifest`. `capability` and `state` decode as strings with an `unrecognized(String)` fallback, so a newer server cannot break an older client and an unknown state renders as "Unknown · Needs a newer Rem" — never silently as Included. A connected source whose last collect failed renders `Unavailable` in amber with its reason ("Connector didn't respond · 2h ago"); a working one shows its item count. That difference used to be invisible in the app and observable only in SQL, which is why the previous hand-written `.active`/`.planned` array was removed. Only a `not_connected` row is tappable, pushing the same Connectors destination as `gateway-connectors-nav`; an `unavailable` row is already connected, so sending the user there would be a dead end. `unavailableReason` is treated as a machine code — known codes get product copy, unrecognized code-shaped values are humanized, and free-form provider error text is replaced with "Last run didn't complete" rather than pasted into the UI. **`state` decides whether that reason is rendered at all**: the server deliberately emits a non-null reason on rows whose state is fine (a recorded `no_active_connection` that a live ACTIVE account has since superseded still travels on an `included` row, because the field reports the last collect and not the current verdict), so the evidence line consults `row.state` first and a healthy row shows its item count instead. Inputs state is owned by the server and changes from outside this screen, so the detail view refreshes on `scenePhase == .active` (returning from the Composio OAuth hand-off in the user's own browser), on `onAppear` (popping back from Connectors), and via `refreshable`; `.task` alone fires once per view identity and left a freshly connected Gmail reading "Not connected" until the view was rebuilt. **Outputs are not authored in the app either.** They come from `GET /api/v1/automations/:kind/outputs` through `AutomationOutputsService`/`AutomationOutputsStore`, which reports `included` / `idle` / `coming_soon` derived from whether a producer is registered and what that producer actually produced for this user — the authored artifact row, `gatherBrief`'s blocked+overdue counts, `deriveSuggestions`' list length. `idle` renders as "Nothing yet": an output reads as not-producing because there is no production record, not because someone typed a status. The literal this replaced said `.planned` for "Suggested tasks" for the entire period when suggestions were shipping and `GET /api/v1/brief` was serving them, and a unit test pinned that literal against itself and stayed green throughout. A real zero count is stated ("Nothing right now") rather than hidden, so an Included row can always say what it produced and when; an unobservable producer degrades to `idle`, never to `included`. Trigger rows remain the sole enable state until the backend can authoritatively enforce capability readiness. Run History labels `lastRunAt` honestly as the latest scheduled processing evidence rather than guaranteed chat/push success. Cached state refreshes in place without flashing a skeleton, while a real-row shimmer is limited to the initial network load. A 404 is explained as a server-update requirement rather than exposed as a raw HTTP error, for both the check-in read and the Inputs read. Custom automation creation and editable prompts remain out of scope until the backend has an authoritative routine contract. Launch DEBUG with `--rem-automations-fixture` for auth-free visual acceptance. |

## Chat Diagnostics

- Live `Working` activity is part of the scrollable transcript tail, not pinned composer chrome.
  It starts collapsed and only a user tap expands it; once expanded its step list is
  height-bounded with internal scrolling. When one persisted content
  item carries both reasoning and final prose, both fields must be projected so history handoff
  cannot clear the streamed response and leave only an Activity disclosure. Live structured
  activity also makes an otherwise-empty, currently bound requested chat render its transcript;
  retained prior-route activity cannot bypass the history skeleton. It follows the bottom only when
  the run first becomes active, preserving a reader's scroll position as later steps arrive.
- `SharedRemChatView` keeps `[ChatSanitize]` render-path tracing off by default, even in DEBUG builds, because the chat view can re-render long transcripts many times and repeated raw/cleaned preview logs can balloon debug memory during dogfood sessions. Launch with `REM_CHAT_SANITIZE_VERBOSE=1` only for a targeted sanitization investigation.
- Chat history is gateway-backed. The app caches local display names,
  timestamps, and previews for polish, but the canonical session list and
  transcript come from the active gateway's `sessions.list` and `chat.history`
  RPCs. Switching to a different gateway can make old chats disappear from the
  current app view unless those sessions exist on the new gateway too.

## Gateway-backed Model Management Contract

- The active gateway's `agents.defaults.models` is the source of truth. Missing or empty means
  Automatic is on and any configured model is eligible; a non-empty map is the explicit allowlist.
- Turning Automatic off materializes the currently usable catalog into that allowlist. Turning it
  on removes the allowlist. Neither action changes `agents.defaults.model.primary` or a session's
  selected model.
- MiniMax M2.7 mutates the same allowlist using OpenClaw's canonical exact-ref and `provider/*`
  matching. Disabling it replaces a matching provider wildcard with explicit sibling refs so the
  rest of that provider is not accidentally disabled. It cannot be disabled while it is the
  configured primary, or when doing so would leave Rem with no remaining catalog model whose
  provider the active runtime has independently verified as authenticated.
- Every write starts from a fresh `config.get` hash, uses `config.patch`, and verifies a short,
  authoritative config readback projected over the already-complete catalog. Ambiguous transport
  acknowledgements get a bounded replacement-connection window; structured gateway rejections
  rebase immediately. Readback confirms the requested effective switch state even when OpenClaw
  normalizes model metadata; rollback still requires exact subtree ownership, so normalized or
  newer cross-device metadata is never overwritten.
- There is no UserDefaults mirror. Another signed-in device sees the authoritative setting on its
  next load. Old gateways that reject `models.list`'s configured-view parameter fall back to the
  original RPC shape. Older gateways, explicitly partial catalogs, and gateways without the full-
  catalog view may render Automatic from config and positive currently-effective rows read-only.
  MiniMax still requires exact primary/provider-model identity plus positive runtime auth; all
  switches remain disabled with an update explanation until both catalogs prove completeness.
- Mutable model settings require both `view=all` and `view=configured` to report
  `catalogComplete: true`. A known-partial response and a legacy pair with no completeness metadata
  are explicitly read-only. Neither can materialize an incomplete choice catalog or effective set
  into a destructive allowlist.
- Models settings receive provider evidence as a tri-state. Loading/failure without a retained
  verified snapshot shows loading or reconnect recovery and cannot expose mutation controls;
  verified empty is the only state allowed to claim that no other providers are available.
  MiniMax requires exact managed identity plus positive runtime-auth evidence in every catalog
  mode. A partial legacy catalog with no such evidence omits the MiniMax row instead of rendering
  unknown state as OFF; a complete catalog may truthfully render verified absence as disabled OFF.

## Copy Conventions

- Gateway detail actions should name the user-facing object: `Connect Gateway`, `Reconnect Gateway`, `Switch to This Gateway`, and `Remove Gateway`.
- Trust-revocation recovery should stay device-specific: put reset/re-pair actions inside the affected device detail when a device row exists, and use `Reset Pairing` as the verb.
- Avoid mechanical labels like `Connect This Connection`; they read like internal model names instead of recovery actions.
- Use `remPrimaryActionButton()` for launch/onboarding/consent and primary approval CTAs; it intentionally mirrors the sign-in button style. Use `remSettingsCTA(_:)` for text-only grouped-list actions and `remInlineRecoveryCTA(_:)` for softer recovery-card actions. Button-only list rows should remove row insets/background so the button does not read as a nested card. Inspect `RemSettingsCTAButtonStyle.swift` for the canonical light/dark CTA preview matrix before introducing a new button style.
- Pairing recovery has one destination: **Paired Devices**. Agenda/launch recovery and Chat recovery both route to `SharedGatewayDevicePairingScreen`; the screen owns managed-cloud approval, pending requests, and paired-device state. Do not strand a second approval action in gateway detail or make a list-only refresh look like it repairs cloud pairing.
- Use `ContainedIcon` for compact rounded icon tiles across Settings, Gateway, Onboarding, and Mac surfaces. `SettingsIcon` remains a compatibility alias for older call sites; new shared UI should use the app-wide component name.
- Do not use TipKit for blocking or semi-blocking gateway recovery. TipKit belongs to optional first-use education; gateway connection, approval, retry, and reset states remain operational recovery UI.
